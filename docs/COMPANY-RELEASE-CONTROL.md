# Manual software updates

Production follows `release/production`, not `main`. Set `RELEASE_CONTROL_ENABLED=true` on all application services. Main is the candidate source; checking or pushing code never starts an update. `/api/version` identifies a commit rather than a container deployment, so restarts do not create new software versions.

Software Update shows a direct **Update** button. An active, unexpired ACTIVE/TRIAL company administrator with `company:EDIT`, or a platform administrator with `system:MANAGE`, can request the exact candidate SHA through CSRF-protected POST `/api/releases/update`. One click records an audited, idempotent `software-release-request:<SHA>` and starts the shared release queue. There is no confirmation dialog or company-approval collection. The retired approval endpoint returns 404 and old approval records are ignored. A changed candidate needs a new manual request; duplicate clicks across companies create one request and one audit event.

The public `/api/releases/deployable` endpoint returns only the manually requested candidate SHA or null. Status exposes no requester identity or company approval counts. The scheduled Manual Software Update workflow checks about every five minutes (GitHub scheduling can be delayed), requires a successful main-push TCW HR Verification run for that exact SHA, verifies forward history, then advances `release/production` without force. Railway follows this controlled branch. Repository-scoped GITHUB_TOKEN handles the branch update; no Railway credentials reach the application or browser.

The three portals and all companies use a shared production version. One authorized update request deploys to all of them; it does not wait for other companies. Queued means requested, not installed: the running version changes only when Railway deployment succeeds. Open browsers never auto-reload; Update appears when a new production version is ready for this open device and loads its current files explicitly. No Update action appears when the software is current or the release is already queued. New code remains a candidate until an administrator chooses Update. Do not switch production back to main. Policy changes may be bootstrapped by a deliberate operator rollout authorized by the user.

Release notifications retain the atomic once-per-commit claim, stable event-tag deduplication across push and foreground delivery, and user-scoped foreground checks. Service workers do not activate automatically on install; the legacy `TCW_ACTIVATE_APPROVED_WORKER` message is retained only for compatibility with waiting workers and has no company-approval semantics. HTML and authenticated API data are never pinned or cached by this mechanism.
