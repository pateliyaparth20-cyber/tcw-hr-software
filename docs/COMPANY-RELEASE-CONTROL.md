# Company-approved shared production releases

Production must follow `release/production`, not `main`. Set `RELEASE_CONTROL_ENABLED=true` on all application services. The public repository's main branch is the candidate source; failed source checks keep the running release active. `/api/version` now identifies a commit, not a container deployment, so restarts do not count as new software versions.

The Software Update page lets a company user with `company:EDIT` approve the exact available SHA. Approval is CSRF-protected, audited, tenant-scoped and invalidated by a new candidate. Every ACTIVE or TRIAL company must approve before the shared production branch advances. With no active companies, a platform administrator with `system:MANAGE` must approve. Platform administrators cannot bypass company approvals. The public deployable endpoint exposes only the approved SHA or null.

The scheduled Approved Company Release workflow checks readiness approximately every five minutes (GitHub scheduling can be delayed), requires a successful main-push TCW HR Verification run for that exact SHA, and advances `release/production` without force. Railway services follow this branch. The workflow uses the repository-scoped GITHUB_TOKEN; no Railway credentials are sent to browsers or stored by the application. An approval means queued approval, not a completed installation. Railway build completion determines when users receive the new release; open browsers are never automatically reloaded.

This hosting architecture shares a release across all companies. It does not let different companies run independent application versions. A company that has not approved blocks the rollout for everyone; the Update page explains this. Independent company release timing would require separate versioned deployments and tenant routing. Do not switch production back to main or manually advance the production branch to an unapproved SHA. Emergency releases require a deliberate operator action outside this approval workflow.

Release notifications use an atomic database claim keyed by commit SHA, so replicas and restarts cannot send another batch for the same release. Worker delivery is serialized and remembered per event tag for the latest 200 events; push and foreground fallback use the same event ID. Foreground notification checks are scoped to the signed-in user and avoid dispatch when a registered push subscription is active. Service workers no longer call skipWaiting during install. Cache activation on an open device is a manual action; closing all tabs follows the browser's normal worker lifecycle. HTML and authenticated API data are never pinned or cached by this release mechanism.
