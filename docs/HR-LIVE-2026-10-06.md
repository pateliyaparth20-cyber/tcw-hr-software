## Payroll concurrency hardening

Attendance reconciliation/locking, payroll preparation/finalization/reopening,
run deletion, adjustments, manual corrections/punches, leave changes and the
legacy current-month repair share a tenant/month transaction lock. Payroll
preparation now reconciles and locks attendance in the same transaction as the
calculation, so a failed preparation rolls those changes back. Repeated
finalization reports whether the transition occurred, preventing duplicate
payslip notifications from concurrent requests.

Payout requests claim employees under that same lock before contacting the
provider, then release database locks before network I/O. Repeated Pay requests
skip every existing transfer, including INITIATING, FAILED and UNKNOWN. An
unverified/timeout response is UNKNOWN, not evidence of failure, and cannot
trigger another automatic transfer. Configuration/bank checks precede claims.
The dialog explains this behavior and displays transfer errors. Provider sync
validates the response and ignores overlapping stale status updates.

This deliberately prioritizes avoiding duplicate transfers. UNKNOWN or stuck
INITIATING rows require provider-dashboard reconciliation; automated recovery,
verified retry attempts, dispatch outbox and provider webhooks remain follow-up
work. No live payments or credential checks were made. Test providers only use
synthetic employees and return synthetic responses.

Verification includes the embedded PostgreSQL regressions and a separate CI
PostgreSQL 16 service for actual simultaneous connections and advisory-lock
waiting. The concurrency script refuses non-loopback database hosts and any
database name other than tcw_payroll_test. Full build/browser and concurrency
results are recorded on the corresponding PR.
