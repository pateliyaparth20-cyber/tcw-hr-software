# TCW HR Software v1.1 — Production Blueprint

This document combines the three launch views requested for v1.1: (1) page-by-page product structure, (2) role-wise workflows, and (3) the release checklist / launch priority.

## 1. Page-by-page production structure

### Public / acquisition

| Page | Purpose | Production behavior |
| --- | --- | --- |
| `/login` | Company sign-in | Company code + email/login ID + password, password recovery, link to self-service trial signup. |
| `/signup` | Self-service trial | Creates a tenant, company owner, generated company code, default leave policies and a 3-day trial. The new tenant appears automatically in the SaaS Admin company portfolio. |
| `/forgot-password` / `/reset-password` | Recovery | Uses the outbox/email worker and time-limited reset tokens. |
| `/downloads` | App delivery | PWA install plus configured Android APK / Windows installer links. Native buttons stay disabled until signed release URLs are configured. |

### Company HR portal

| Workspace | Main capabilities |
| --- | --- |
| Dashboard | Workforce command center, attendance exceptions, leave, payroll state, device health, support pressure, recent activity and on-demand AI brief. |

| Organization | Branches, departments, designations, teams, locations and cost centers. |

| Leave | Leave types, requests, balance/overlap rules, approval/rejection and history. |
| Calendar | Month/week/day/agenda experience for holidays, leave, interviews, payroll milestones, training and company events. |
| Payroll | Attendance-backed monthly runs, deductions, review, approval, final lock, employee payslips, adjustments and bank payout CSV. |
| Recruitment | Jobs and candidate pipeline. |
| Expenses / Travel | Employee-submitted operational workflows with review permissions. |
| Training / Goals / Assets / Exit | Workforce lifecycle modules within the same tenant. |
| Documents | Authorized file storage backed by configured S3-compatible storage. |

| Notifications | Unified timeline, unread/priority filters, mark-one / mark-all read and operational alerts. |
| Support | Ticket number, category, priority, SLA due time, status, response history and company-facing support workspace. |

### TCW SaaS / Super Admin portal

| Workspace | Main capabilities |

## 2. Role-wise workflows

### TCW Super Admin

1. Signs in through the dedicated Admin portal.
2. Sees every self-service trial and manually provisioned company in the company portfolio.
3. Reviews trial state, plan, usage, billing and support pressure.
4. Activates/suspends/expires companies as policy requires; non-active access revokes tenant sessions where applicable.
5. Records payments / manages invoices until a live gateway is configured.
6. Handles tickets in the Support Command Center.
7. Configures the AI provider once in System Health; API keys are encrypted at rest and not returned to the browser.
8. Uses platform audit trails for operational accountability.

### Company Owner / HR Admin

1. Self-signs up or receives a provisioned company account.
2. Sets company profile, branches, departments, shifts and attendance rules.
3. Adds employee A-to-Z records and, when needed, creates application users linked to employees.
4. Maps BioMax enrollment IDs / employee codes and checks device health.
5. Reviews leave, attendance corrections, missing punches and monthly attendance.
6. Locks attendance only after exceptions are resolved.
7. Calculates payroll from the locked attendance month, then reviews / approves / locks payroll.
8. Exports payout CSV or uses a configured payout provider once a production payout integration is approved.
9. Receives operational notifications and can open support tickets from the same portal.

### Manager / Team Leader

1. Uses scoped access for own/team records.
2. Reviews permitted leave/attendance workflows.
3. Uses the calendar, notifications and team-facing operational views.
4. Does not receive unrestricted company payroll or employee master access unless the role permissions explicitly allow it.

### Employee

1. Signs in under the employer's company code with a linked employee account.
2. Views permitted own-profile information, attendance / requests and finalized payroll records.
3. Submits supported employee requests such as leave and permitted expense/travel workflows.
4. Receives personal notifications such as leave outcomes and finalized payslip availability.

### Self-service prospective customer

1. Opens `/signup` and chooses a plan for the trial.
2. Enters company/owner information and creates a strong password.
3. Receives a generated company code and is signed into the new tenant immediately.
4. Trial status and the new company appear automatically in the TCW Admin portal.
5. Trial access expires according to `TRIAL_DAYS` unless the subscription is activated.

## 3. Launch checklist and priority

### P0 — required before public launch

- [ ] Real production PostgreSQL instance; never use embedded PGlite demo storage publicly.
- [ ] Redis available for worker queues.
- [ ] HTTPS for HR/Admin endpoints and secure cookies enabled.
- [ ] Strong unique `ADMIN_PASSWORD`, PostgreSQL password and `CONFIG_ENCRYPTION_KEY` stored in a secret manager (`npm run production:secrets` can generate starting values).
- [ ] `SEED_DEMO=false`; do not seed fictional demo employees/candidates in production.
- [ ] `PUBLIC_SIGNUP_ENABLED=true` only after terms/privacy and abuse controls are accepted for launch.
- [ ] Production SMTP configured and password-reset email tested end-to-end.
- [ ] S3-compatible file storage configured and upload/download authorization tested.
- [ ] Database backup + restore procedure tested.
- [ ] Run `npm run production:check`, `npm run typecheck`, `npm test`, `npm run test:integration`, `npm run build`, and browser smoke tests in the deployment environment.
- [ ] Reverse proxy / edge TLS configured in front of localhost-bound application ports.
- [ ] Verify tenant isolation with at least two non-demo companies before opening registration.

### P1 — required for the intended commercial workflow

- [ ] Test self-signup -> company code -> first dashboard -> Admin company portfolio.
- [ ] Test 3-day trial expiration and billing-lock behavior.
- [ ] Test notification center for leave, support, device, employee and payroll events.
- [ ] Test BioMax device model / firmware in the real client network.
- [ ] Reconcile attendance and verify payroll results with company-approved salary rules.
- [ ] Review payroll statutory configuration with a qualified payroll/compliance professional before relying on PF/ESIC/PT/TDS calculations.
- [ ] Publish signed Android APK and Windows installer, then set their release URLs.
- [ ] Configure AI provider and verify model/data boundaries.

### P2 — external-provider production integrations

These cannot be made real by source code alone and must be completed with approved provider credentials, KYC and webhook/security configuration:

- [ ] Online subscription payment gateway.
- [ ] Unattended employee bank payouts / salary transfer.
- [ ] SMS / WhatsApp delivery.
- [ ] Production biometric connectivity over public networks where required.
- [ ] App-store / code-signing distribution for native applications.

## Salary / leave / attendance calculation boundary

The v1.1 flow calculates employee monthly payroll from locked attendance, approved leave, stored monthly salary, active salary rules and adjustments, and presents gross/deductions/net plus attendance units on the employee's finalized payroll record. This is an HR/payroll engine, not a legal certification of statutory payroll. Production tax/statutory rules must be reviewed for the employer's jurisdiction and current rules before payroll approval.

## Production login model

There is deliberately no universal public production password in this archive.

- **TCW Super Admin:** configured through `ADMIN_EMAIL` + `ADMIN_PASSWORD` in production secrets, then created by `npm run db:seed`.
- **Self-service Company Owner:** chooses a password on `/signup`; the platform generates the company code and owner login ID.
- **Provisioned Company Owner:** receives credentials created by the TCW Admin provisioning flow.
- **Employees / Managers / HR users:** created inside their tenant and linked to the appropriate employee record/role.

This prevents a shared default password from becoming a launch vulnerability.
